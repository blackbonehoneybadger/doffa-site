# Полный аудит DOFFA: сайт и игра

**Дата:** 2026-08-19  
**Репозитории:** `blackbonehoneybadger/doffa-site`,
`blackbonehoneybadger/Doffa-Archer`  
**Цель:** понять фактическую готовность, найти уязвимости и утечки, исправить
безопасно устранимые проблемы и отделить готовый продукт от планов.

## Короткий итог

- В истории `doffa-site` **не найдено реальных API-ключей, приватных ключей,
  seed-фраз, keypair-файлов или строк БД с паролем**.
- В корневом production-приложении после обновления — **0 известных
  уязвимостей по `npm audit`**. До исправления было 7: 6 high и 1 moderate.
- Исправлены защита API, обработка секретов и ошибок, лимиты запросов,
  безопасность Blob URL, миграции БД, приватность счётчика, mainnet-скрипты,
  security headers и CI.
- `Doffa-Archer` сейчас **полностью пуст**: нет коммитов, веток с кодом,
  package-файлов, игры, тестов и сборки. Это главный продуктовый блокер.
- Отдельная папка `token/` не входит в сайт, но её legacy-цепочка
  Solana/Metaplex всё ещё имеет **13 известных проблем: 3 high и 10 moderate**.
  Для основной high-проблемы `bigint-buffer` патча нет. Риск изолирован и
  задокументирован, но не считается закрытым.
- На живом сайте честно отмечены незавершённые функции: новый Reward Vault не
  назначен, claims тестируются, burn/DEX/APK и браузерная игра готовятся.

## Область и ограничения проверки

### `doffa-site`

Проверены:

- рабочее дерево и архитектура Next.js;
- все 13 загруженных remote refs и 141 исторический коммит до audit-коммита;
- 695 уникальных git blobs: 661 текстовый и 34 бинарных;
- корневые и отдельные `token/` зависимости;
- API-маршруты, auth, БД, Blob, внешние интеграции и token-операции;
- тесты, типы, линтер и production-сборка;
- фактически опубликованные страницы `doffa.coffee`.

### `Doffa-Archer`

GitHub возвращает пустой репозиторий (`size: 0`, default branch `main`, история
коммитов отсутствует). Проверять безопасность игры пока физически нечего.

### Что нельзя проверить из git

Аудит репозитория не читает фактические значения секретов в Vercel, Neon,
Vercel Blob, GitHub Actions, RPC-провайдере или локальных кошельках. Поэтому
вывод «утечек нет» относится к доступной git-истории и файлам, а не доказывает,
что внешние окружения настроены правильно.

На 2026-08-19 прямой live-check подтвердил, что главная больше не содержит
Crazy 8 и «1 чашка = 1 токен»; она показывает DOFFA Heroes. `/game` помечает
игру как готовящуюся, `/download` не выдаёт несуществующие ссылки, а
`/transparency` показывает неназначенный Reward Vault и supply 100 млн против
99 млн фактически доступных токенов. Поисковый индекс всё ещё отдаёт старый
snippet с Crazy 8 — после следующего деплоя нужна повторная индексация.

## Проверка секретов и персональных данных

Сканер проверяет полную git-историю, а не только текущий checkout:

- PEM/private-key блоки;
- Solana JSON keypair и длинные base58-секреты;
- GitHub, OpenAI, Stripe, Slack, AWS, Google, npm, GitLab, SendGrid, JWT и
  Vercel Blob шаблоны;
- credentialed PostgreSQL/MySQL/MongoDB URL;
- подозрительные имена `.env`, `owner.json`, `*.pem`, `*.key`, `id_rsa`,
  `*.p12`, `*.pfx`, service-account и keypair-файлов.

Результат: **0 находок, требующих ротации**. В allowlist внесены восемь точных
path+fingerprint правил: два учебных credential URL, генерируемый тестовый
secret, собственный PGP-шаблон сканера и четыре path-ссылки на три публичные
Solana transaction signatures. Allowlist не построен на широком исключении
пути или регулярного выражения.

В metadata исторических коммитов есть личный e-mail автора. Это публичная
privacy-информация, не credential. Переписывать историю ради неё не стоит;
для будущих коммитов можно включить GitHub noreply-адрес. Адрес кофейни,
WhatsApp и публичные Solana-адреса на сайте являются намеренно опубликованными
бизнес/on-chain данными, а не секретами.

## Найденные проблемы и исправления

| Приоритет | Проблема до аудита | Исправление | Статус |
|---|---|---|---|
| High | Next.js 16.2.9 и transitive deps: 7 advisories | Next.js/ESLint config обновлены до 16.3.1, lockfile безопасно обновлён | Закрыто, root audit = 0 |
| High | `token/`: 13 legacy advisories | Папка изолирована от Vercel, добавлены правила безопасного запуска | Остаточный риск; нужна миграция deps |
| Medium | `SESSION_SECRET` мог стать случайным на каждом production-инстансе | Production auth теперь fail-closed; README требует отдельные секреты | Закрыто кодом; env обязателен |
| Medium | Изменяющие API не проверяли origin | Добавлена same-origin/`Sec-Fetch-Site` проверка для auth/logout/profile/admin/merch/track | Закрыто |
| Medium | Неограниченное `request.json()` позволяло расходовать память | Streaming-limit 16 KiB, корректные 400/413/415 | Закрыто |
| Medium | Тексты ошибок SDK/БД могли попасть клиенту или целиком в лог | Унифицированы безопасные ответы и минимальный structured log | Закрыто |
| Medium | Админ-auth мог падать неуправляемо при сбое БД | Единый fail-closed guard возвращает 503, а не допускает операцию | Закрыто |
| Medium | Blob-манифест принимал недостаточно строго связанные URL/path | Только HTTPS, точный Vercel Blob host/path, допустимое расширение, без credentials/query/hash | Закрыто |
| Medium | Mainnet `create`/`burn`/`revoke` не требовали сильного подтверждения | Одновременно нужны временная env-фраза и CLI-флаг с точным mint | Закрыто |
| Medium | Burn использовал `Number`/`Math.round`, допуская ошибку количества | Точный decimal → bigint parser, ограничения decimals/supply/memo | Закрыто |
| Medium | SQL-схема делала `DROP TABLE` rate-limit таблицы при миграции | Новая additive/idempotent таблица без удаления данных | Закрыто |
| Low | Публичный `/api/track` можно было накручивать и раздувать БД | Один HMAC(IP+UA) в день, без хранения raw IP, retention 31 день | Закрыто |
| Low | Rate limit доверял обычному forwarded header без нормализации | Приоритет `x-vercel-forwarded-for`, строгая нормализация, fallback | Закрыто |
| Low | Honeypot формы был логически недостижим | Схема принимает поле и тихо отбрасывает bot-submit до записи | Закрыто |
| Low | Серверные config-модули защищались только соглашением | Установлен `server-only`, добавлены обязательные imports | Закрыто |
| Low | Не было CSP/frame/nosniff/referrer/permissions headers | Добавлены централизованные security headers и отключён `X-Powered-By` | Готово к деплою |
| Low | Не было постоянного CI/security scan | Добавлены pinned GitHub Actions, Dependabot, audit/lint/types/tests/build/full-history scan | Закрыто |

До деплоя live-ответ главной содержит HSTS, но не содержит CSP,
`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и
`Permissions-Policy`. Исправление находится в этой ветке и станет фактической
защитой только после деплоя.

Текущий CSP — совместимый baseline, а не максимальный режим: Next.js bootstrap
и существующая тема пока требуют `'unsafe-inline'` для scripts/styles. Переход
на nonce-based CSP возможен, но сделает страницы динамическими и требует
отдельного performance/regression проекта; его нельзя включать вслепую в
security hotfix.

## Ветки и риск конфликтующей миграции

В `doffa-site` загружено 13 remote refs. Ветка
`migration/new-doffa-token` на 13 коммитов впереди `main` и не отстаёт от него.
Она содержит отдельный сценарий выпуска нового токена и удаление информации о
нынешнем токене со страниц. Это не обычный security fix и **не должно вливаться
автоматически**: оно меняет публичную экономику, runbook и источник истины.

Рекомендация: сначала принять отдельное бизнес-решение — сохраняется текущий
mint или действительно выпускается новый, — затем провести отдельный diff-аудит
13 коммитов и перенести только согласованные изменения. Остальные старые ветки
не удалялись: удаление — отдельное организационное решение владельца.

## Что сделать перед merge/deploy

1. В Vercel проверить наличие разных случайных значений длиной не менее 32
   символов: `SESSION_SECRET` и `ADMIN_SESSION_SECRET`; также проверить
   `ADMIN_UPLOAD_PASSWORD`.
2. Проверить подключение Postgres (`DATABASE_URL` или `POSTGRES_URL`) и Blob
   (`BLOB_READ_WRITE_TOKEN`). Не присылать значения этих переменных в issue/PR.
3. Выполнить `npm run migrate` на production-БД. Это создаст
   `admin_login_limits` и `site_visit_days` без удаления старых данных.
4. Создать Vercel preview и проверить: wallet login/logout, profile PATCH,
   admin login/video upload/delete, merch order, security headers и console.
5. Только после smoke-test влить PR в `main` и проверить production ещё раз.
6. Запросить переиндексацию главной, чтобы убрать старый Crazy 8 snippet.
7. Загрузить реальный исходный код игры в `Doffa-Archer`; до этого нельзя
   считать игру сохранённой, собираемой или аудированной.
8. Отдельно спланировать обновление legacy Solana/Metaplex зависимостей. До
   него запускать `token/` только на изолированной машине по новому runbook.

## Приоритетный продуктовый backlog

1. **P0 — сохранить игру:** наполнить `Doffa-Archer`, добавить README/license,
   воспроизводимую сборку, CI и минимальные тесты.
2. **P0 — включить безопасный сайт:** env → миграция → preview smoke-test → merge.
3. **P1 — Reward Vault:** новый кошелёк только после двух независимых backup и
   проверенного восстановления; затем публичный адрес и финансирование.
4. **P1 — claims/security:** серверная верификация забега, replay protection,
   лимиты, anti-cheat, ledger, идемпотентность и тестовые выплаты.
5. **P1 — release:** web URL и/или подписанный APK с version + SHA-256.
6. **P2 — marketplace:** seller onboarding/moderation, checkout, payment
   reconciliation, fulfilment/refunds и privacy retention.
7. **P2 — token tooling:** заменить уязвимую legacy dependency chain и только
   после этого снять режим усиленной изоляции.
