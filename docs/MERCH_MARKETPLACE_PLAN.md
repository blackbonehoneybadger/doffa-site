# DOFFA Marketplace — аудит, архитектура и поэтапный план

Дата: 2026-07-15. Раздел «Мерч» превращается в маркетплейс **DOFFA Merch / DOFFA Marketplace**
внутри официального сайта (`/merch`), без отдельного приложения и без переноса в игру.

Главные правила: (1) в «Мерч» нет еды; (2) продавцы сами добавляют товары после одобрения;
(3) есть отдельное направление изделий из кожи на заказ; (4) DOFFA — дополнительный способ
оплаты, не единственный; (5) не выдумываем товары/оплаты/отзывы; (6) реальные платежи не
включаются без серверной проверки.

## Аудит исходного состояния

`/merch` был одностраничным лендингом «кожа на заказ + коллекция DOFFA + честная форма заявки»
(WhatsApp-фолбэк, без фейкового успеха). Не было: каталога товаров, продавцов, корзины,
оформления заказа, оплаты (fiat/DOFFA), страниц товара, кабинета продавца, админ-модерации,
юридических страниц маркетплейса, БД-сущностей маркетплейса.

## Что сделано в этом этапе (Этап 1 + фундамент)

### Новая структура `/merch`
- Хаб с тремя направлениями: **Готовые товары**, **Изделия из кожи на заказ**, **Стать продавцом**.
- Hero «Фирменные товары и изделия на заказ», три CTA.
- Каталог с честным пустым состоянием: «Товары появятся после публикации продавцами» (флаг `catalogEnabled` по умолчанию выкл).
- FAQ маркетплейса, ссылки на юридические страницы.

### Новые маршруты
- `/merch` — хаб.
- `/merch/custom-leather` — полный поток кожи на заказ (категории, персонализация, 5 шагов, честная форма, коллекция DOFFA).
- `/merch/become-a-seller` — заявка продавца (honest: канал связи, без фейковой регистрации).
- `/legal/merch`, `/legal/sellers`, `/legal/returns`, `/legal/payments` — юридические черновики (требуют юриста).

### Фундамент (архитектура для Этапов 2–8)
- `app/config/merch.ts` — публичная конфигурация: название площадки, **feature flags** (все production-функции без интеграции ВЫКЛ по умолчанию), статусы товара/продавца/заказа/кастомной заявки, публичные параметры оплаты в DOFFA (mint, decimals, TTL котировки), лимиты и MIME загрузок, FAQ.
- `app/config/merch.server.ts` — **серверная** конфигурация секретов (не `NEXT_PUBLIC`): комиссия, admin email, DB URL, storage token, секрет платёжного провайдера, адрес-получатель DOFFA, ключ price-провайдера, RPC. Импортируется только серверным кодом.
- `db/schema.sql` — сущности маркетплейса: `merch_sellers`, `merch_seller_applications`, `merch_categories`, `merch_products`, `merch_product_variants`, `merch_product_images`, `merch_uploaded_assets`, `merch_orders_shop`, `merch_order_items`, `merch_payments`, `merch_doffa_quotes`, `merch_shipments`, `merch_audit_log` + расширение `merch_orders` (кастомные заявки: `ref`, `status`, …). CHECK-и на все enum-статусы; `unique(tx_signature)` — одна транзакция не оплачивает два заказа.
- `app/lib/payments/provider.ts` — интерфейс `PaymentProvider` (createPayment/verifyPayment/refundPayment/getPaymentStatus) + dev-only mock, который **никогда** не создаётся в production и **не** подтверждает оплату.
- `app/lib/payments/doffa.ts` — чистая логика оплаты в DOFFA: расчёт котировки (`computeDoffaQuote`), проверка истечения (`isQuoteExpired`), серверная проверка транзакции (`verifyDoffaPayment`: mint, получатель, decimals, финальность, TTL, недоплата, повторное использование, tolerance), разбивка комиссии (`splitOrderAmounts`).
- `test/merchPayments.test.ts` — юнит-тесты этой логики.

## Как это будет работать (по этапам)

### Как добавляются продавцы
Заявка (`/merch/become-a-seller`) → `merch_seller_applications` (status `under_review`) → админ
одобряет → создаётся `merch_sellers` (status `approved`). Публично видны только `approved`.

### Как добавляются товары
Продавец в кабинете (`/merch/seller`, Этап 3) создаёт товар → он попадает в `merch_products`
со статусом `moderation` → админ (`/admin/merch`) одобряет → товар становится публичным.
Статусы `hidden`/`moderation` публично не показываются.

### Как работает модерация
`/admin/merch` (Этап 3): одобрение/отклонение/приостановка продавцов, проверка/скрытие товаров,
категории, комиссия, заказы, споры, журнал (`merch_audit_log`). Права проверяются **на сервере**
(существующая admin-сессия), не только на клиенте.

### Как работает кастомный заказ
`/merch/custom-leather` — форма с загрузками (логотип/эскиз/референсы), серверная валидация,
лимит размера, антиспам; статусы New→…→Completed. Сейчас — honest WhatsApp-фолбэк (без фейкового
успеха); онлайн-приём с сохранением в БД включается флагом + миграция.

### Как устроена корзина
Этап 5: несколько товаров, варианты, количество, сохранение между сессиями, подытог, доставка,
итог, выбор оплаты. Мульти-вендорность: заказ разбивается на подзаказы по продавцам
(`merch_orders_shop.seller_id`) либо смешанная корзина запрещается до готовности логистики —
этот нюанс не скрывается.

### Как работает обычная оплата
Через `PaymentProvider` adapter. Пока провайдер не выбран владельцем — UI показывает
«Обычная онлайн-оплата подключается», mock только в dev, в проде оплата не принимается.

### Как проверяется оплата в DOFFA
Клиент не подтверждает оплату. Сервер по RPC извлекает параметры транзакции и вызывает
`verifyDoffaPayment`: mint, отправитель, получатель, сумма, decimals, подпись, финальность,
отсутствие повторного использования, соответствие заказу, TTL котировки. При успехе — статус
`paid`, сохранение подписи, ссылка на Solscan, уведомление продавца. Приватные ключи —
только на сервере, не в `NEXT_PUBLIC_*`, не в bundle.

## Оставшиеся этапы

- **Этап 2** — каталог из БД, страницы товара, поиск/фильтры/сортировка, empty states.
- **Этап 3** — продавцы: кабинет `/merch/seller`, админ `/admin/merch`, модерация, изоляция данных, API продавца/заявок с серверной проверкой ролей.
- **Этап 4** — загрузки файлов (валидация, лимит, безопасная обработка SVG, thumbnails) для кастомных заказов и фото товаров.
- **Этап 5** — корзина + checkout (мультивендорная логика/ограничение).
- **Этап 6** — обычная оплата через реальный adapter.
- **Этап 7** — оплата в DOFFA: серверная RPC-проверка, котировки в БД, идемпотентность подписи.
- **Этап 8** — юридические финализации с юристом, расширение тестов, полировка.

## Внешние сервисы, которые нужно выбрать/подключить
- Платёжный провайдер (fiat) — например, ЮKassa/Stripe (выбирает владелец).
- Хранилище загрузок — Vercel Blob (токен уже используется в проекте для видео).
- Провайдер цены DOFFA (котировки) — источник курса для расчёта цены в DOFFA.
- Адрес-получатель платежей в DOFFA (кошелёк площадки/продавца) + RPC для проверки.
- База данных (Neon/Postgres проекта) + прогон `npm run migrate`.

Ничего из этого не выдаётся за работающее, пока не подключено: соответствующие функции
остаются **Planned** и в UI честно помечены.
